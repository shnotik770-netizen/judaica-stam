# judaica-stam

אתר הזמנות ייעודי לחנות יודאייקה — יצירת הזמנה, הדפסת מדבקה, ותיאום איסוף/מסירה מול ספק הסת"ם.

פרויקט נפרד מהמערכת הפנימית הגדולה של החנות (chabad-judaica). מארח על Railway (מסד נתונים + שרת + אתר), ללא Vercel.

## הרצה מקומית
```bash
npm install
npm start
```

## תשתית
- **קוד**: GitHub — `shnotik770-netizen/judaica-stam`, ענף `main` בלבד (אין branches נפרדים — כל תיקון נכנס ישירות ל-main).
- **אירוח**: Railway בלבד (ללא Vercel) — פרויקט `hazmanat-satam`.
  - שירות `web` — שרת ה-API/אתר (Node+Express). דומיין: `web-production-68f12.up.railway.app`.
  - שירות `Postgres` — מסד הנתונים המנוהל הרשמי של Railway (עם volume אוטומטי לשמירת נתונים).
- **מדפסת מדבקות**: ממשיך להשתמש בפרויקט ה-Supabase הקיים `label-printer` (לא עובר ל-Railway) — זה החיבור היחיד שנשאר מול Supabase.
- **SMS (ימות המשיח / Call2All)**: `lib/call2all.js` — עטיפה ל-API (SendSms, GetIncomingSms, GetSmsOutLog). הטוקן נקרא אך ורק מ-`process.env.CALL2ALL_TOKEN` בצד השרת, **אף פעם לא נכתב בקוד/git**. יש להגדיר אותו ידנית במשתני הסביבה של שירות `web` ב-Railway (Variables tab) — לא דרך קוד או API אוטומטי, כדי שהטוקן לא יעבור דרך שום כלי אוטומציה.

## API

### פנימי (צוות החנות)
- `POST /api/sms/send` — `{phone, message}`
- `GET /api/sms/incoming?limit=&startDate=&endDate=` — הודעות נכנסות אחרונות
- `GET /api/sms/outgoing?limit=` — יומן הודעות יוצאות
- `GET /api/sms/conversation?phone=0501234567` — כל ההתכתבות (נכנס+יוצא) מול מספר ספציפי, ממוינת לפי זמן
- `GET /api/label/:code` (`?type=qr` לברקוד QR, ברירת מחדל Code128) — מדבקת ברקוד לשקית, תמונת PNG
- `POST /api/orders` — יצירת הזמנה+שקיות (`payment: {amount, note?}` לא חובה — תשלום שהתקבל כבר בשעת ההזמנה, נשמר ב-`order_payments` באותה טרנזקציה; `brought_by` לא חובה — "הובא ע"י"; כשמולא, לא משייכים ללקוח קיים לפי טלפון ותמיד נוצר לקוח חדש. `address` לא חובה — ריקה לא מוחקת כתובת קיימת של לקוח מוכר): `{customer:{first_name, last_name, phone, address}, bags:[{item_type, item_type_note?, quantity}]}`. **מספר ההזמנה מונפק אוטומטית** (רץ, `order_number_seq`) — לא מתקבל מהלקוח. **אין מספר לקוח** — לקוח קיים מזוהה לפי `phone` (אם הטלפון כבר קיים, מעדכנים שם/כתובת ומשתמשים באותה רשומה; אחרת נוצר לקוח חדש). מחזיר `order_number` ו-`bag_code` לכל שקית. **מפעיל אוטומטית הדפסת מדבקה לכל שקית** (דרך `lib/printQueue.js`) — תוכן המדבקה: מספר שקית, שם, טלפון, תאריך הזמנה (עברי, ללא ניקוד, דרך `lib/hebrewDate.js`), סוג הפריט. **ללא אימות בכוונה** — החלטת החנות: לא רוצים להתעסק עם מפתחות API בצד הזה, מי שיש לו גישה לאתר יכול ליצור הזמנות.
- `GET /api/orders/customer-lookup?phone=` — אם הטלפון כבר ידוע אצלנו, מחזיר את פרטי הלקוח (כולל `phone` כפי שהוא שמור) + `supplier_customer_number` אם כבר דווח ע"י הספק (ראו `POST /api/supplier/customer-link` למטה). ההשוואה לפי ספרות בלבד (`050-1234567` = `0501234567`). משמש למילוי אוטומטי בטופס הזמנה חדשה כבר בזמן הקלדת הטלפון (ללא אימות)
- `GET /api/orders/customer-search?phone=` — הצעות לקוחות לפי חלק מהטלפון (מ-6 ספרות, השוואה לפי ספרות בלבד בכל מקום במספר, עד 5 תוצאות, התאמה מלאה ראשונה) — לטופס הזמנה חדשה, שמציג אותן כהצעות ללחיצה בלבד (לא ממלא אוטומטית) (ללא אימות)
- `GET /api/orders/customers?q=` — מאגר הלקוחות לטאב "ניהול": כל הלקוחות (עד 500, לפי הזמנה אחרונה) עם `order_count`, `bag_count`, `awaiting_customer_count` (שקיות שחזרו ועוד לא נאספו), `last_order_at`, `supplier_customer_number`. `q` — חיפוש חופשי (שם/טלפון/כתובת, `ilike`) (ללא אימות)
- `GET /api/orders/summary` — `{waiting_pickup, with_supplier}` (ספירת שקיות לכל סטטוס) — לשורת הסיכום המהיר בכניסה לטאב "כל ההזמנות".
- `GET /api/orders/bags?item_type=&status=&collection_number=&q=` — רשימת שקיות עם מסננים, כולל פרטי האיסוף (`collection_number`/`collection_started_at`) אם השקית שייכת לאחד, ותאריך יצירה עברי (`created_at_hebrew`) לכל שורה — למסך "כל ההזמנות" (ללא אימות). `q` הוא חיפוש חופשי (שם פרטי/משפחה/טלפון/קוד שקית/מספר הזמנה, `ilike`). `status` תומך גם בתתי-מצב וירטואליים של "חזר" (לא עמודה אמיתית, רק סינון): `returned_at_store` (חזר, עדיין לא עודכן ללקוח) / `notified` (עודכן, עדיין לא נאסף) / `collected` (נאסף ע"י לקוח) / `not_collected` (חזר ועדיין לא נאסף, בשימוש פנימי ע"י "פעולות מהירות") — בנוסף לערכי הסטטוס הרגילים (`waiting_pickup`/`with_supplier`).
- `GET /api/orders` — רשימת כל ההזמנות + סיכום סטטוס שקיות לכל אחת (`bag_count`, `waiting_count`, `with_supplier_count`, `returned_count`) (ללא אימות)
- `GET /api/orders/:order_number` — צפייה בהזמנה + שקיות, כולל `locked` (true אם אחת השקיות כבר נמשכה בפועל לתוכנה של הספק — `imported_at` — או כבר חזרה — `status='returned'`) — משמש גם את מסך העריכה (ללא אימות)
- `PUT /api/orders/:order_number` — `{customer:{first_name,last_name,phone,address}, bags:[{bag_code,item_type,item_type_note?,quantity}]}`. עריכת פרטי לקוח ופרטי שקיות קיימות (סוג/הערה/כמות — לא מספר שקית). **רק כל עוד ההזמנה לא נעולה** (409 אם כן) — ברגע שהספק כבר קיבל שקית מההזמנה, השינוי חייב לעבור דרכו ולא דרכנו.
- `POST /api/orders/:order_number/bags` — `{item_type, item_type_note?, quantity}`. הוספת שקית חדשה להזמנה קיימת (ממשיכה את מספור השקיות, ומדפיסה לה מדבקה מיד כמו ביצירת הזמנה). רק כל עוד ההזמנה לא נעולה.
- `DELETE /api/orders/:order_number/bags/:bag_code` — מחיקת שקית בודדת מהזמנה. רק כל עוד ההזמנה לא נעולה.
- `DELETE /api/orders/:order_number` — מחיקת הזמנה+שקיותיה. רק כל עוד ההזמנה לא נעולה (ללא אימות)
- `POST /api/orders/scan` — `{bag_codes: [...], action: "notify_manual"|"notify_sms"|"collect", force?}`. מפעיל "פעולה מהירה" בחנות מול הלקוח הסופי, **רק לשקיות שכבר חזרו מהספק**. ה-`action` נבחר מראש ע"י הצוות דרך מסך "פעולות מהירות" (לא מנוחש לפי מצב השקית): `notify_manual` מסמן `customer_notified_at` בלי לשלוח כלום (הלקוח כבר עודכן בדרך אחרת — טלפון וכד'); `notify_sms` שולח SMS אמיתי (דרך `lib/call2all.js`, לפי תבנית מ-`GET /api/orders/settings`) ו**רק אם נשלח בהצלחה** מסמן `customer_notified_at` כמו `notify_manual`; `collect` מסמן `customer_collected_at` ("נאסף ע\"י לקוח"). **קיבוץ לפי טלפון**: `notify_manual`/`notify_sms` מוצאים את כל השקיות של אותו מספר טלפון שעדיין לא עודכנו (`status=returned` וגם `customer_notified_at is null`) ומסמנים את כולן יחד (וב-`notify_sms` שולחים הודעת SMS אחת שמסכמת את כל הפריטים) — כך שאם כמה הזמנות של אותו לקוח חזרו ביחד, מספיק לדווח פעם אחת. ניסיון לדווח שוב על שקית שכבר כוסתה בדיווח קודם מחזיר `action:"duplicate"` עם הסבר ו-`notified_at`. **`force:true`** מדווח/שולח שוב במתכוון גם על שקית שכבר עודכנה — אז הקבוצה כוללת את *כל* השקיות החוזרות של אותו טלפון (לא רק מה שעדיין ממתין), וכל שקית מקבלת רשומת `customer_notified` נוספת ביומן הפעולות (כך שההיסטוריה המלאה — כל הפעמים שדווח על שקית — נשמרת, אפשר לראות אותה דרך `GET /api/orders/activity-log?bag_code=`). ה-UI מציג אזהרת אישור (`confirm`) לפני שליחת `force`. תומך בכמה שקיות בבת אחת (קליק על שורה ברשימה שולח קוד אחד, סריקה מהירה שולחת אחד בכל פעם). מחזיר `{results: [{bag_code, ok, action: "notified"|"collected"|"duplicate", order_number, customer, grouped_bag_codes?, repeat?, message?, notified_at?} | {bag_code, ok:false, error}]}`. ללא אימות (כמו שאר `/api/orders`).
- `GET /api/orders/settings` / `PUT /api/orders/settings` — `{sms_notify_template}`. תבנית הודעת ה-SMS של `notify_sms`, ניתנת לעריכה במסך "ניהול" בלי דיפלוי קוד. `{items}` בתבנית מוחלף בסיכום הפריטים המקובץ (למשל "2 מזוזות, תפילין זוג"). ברירת המחדל: `{items} חזרו מבדיקת סת"ם ומחכים לך ביודאיקה פלוס חב"ד.` — נשמרת ב-`settings` (טבלת key/value).
- `POST /api/orders/:order_number/payments` — `{amount, method?, note?}`: תשלום שהתקבל על ההזמנה (בד"כ בשעת המסירה). `method` אחד מ: מזומן / אשראי / העברה בנקאית / ביט / פייבוקס / צ'ק / אחר. לא תלוי בנעילה. `DELETE /api/orders/:order_number/payments/:id` — מחיקה. שניהם נרשמים ביומן ההזמנה (`payment_added`/`payment_deleted`, מוצגים גם בהיסטוריית כל שקית שלה). `GET /api/orders/:order_number` מחזיר `payments` ו-`paid_total`; `GET /api/orders/bags` מחזיר `paid_total`.
- `POST /api/orders/bags/:bag_code/reprint` — מדפיסה שוב את המדבקה של שקית קיימת (אותו תוכן/ברקוד כמו ביצירה), בלי לשנות שום מצב. עובד גם על הזמנה נעולה. כל שימוש נרשם ביומן הפעולות (`label_reprinted`).
- `PUT /api/orders/bags/:bag_code/force-status` — `{status: "waiting_pickup"|"with_supplier"|"returned", reset_notified?, reset_collected?}`. תיקון ידני למסך "ניהול" — **עוקף במתכוון את הנעילה**, לתיקון טעויות בלבד (למשל סריקה שגויה). לא מנהל קשרים (collection וכו') כמו שאר הנתיבים — שינוי ישיר של status בלבד. כל שימוש נרשם ביומן הפעולות (`manual_fix`).
- `GET /api/orders/bags/:bag_code/reports` — דוחות הספק על שקית (מהחדש לישן, עם `received_at_hebrew`) — למסך העריכה. `GET /api/orders/bags` ו-`GET /api/orders/:order_number` מחזירים גם `report_received_at`.
- `GET /api/orders/activity-log?limit=&bag_code=&q=` — יומן הפעולות האחרונות (יצירה/עריכה/מחיקה/סריקה/תיקון ידני/הדפסה חוזרת וכו', ראו טבלת `activity_log`) — למסך "ניהול" (ברירת מחדל 100, מקסימום 500). `bag_code` — התאמה מדויקת, להיסטוריה המלאה של שקית ספציפית (מסך העריכה). `q` — חיפוש חכם (`ilike`) לתיבת החיפוש בטאב "ניהול": מתאים לפי קוד שקית/מספר הזמנה **וגם** לפי שם פרטי/משפחה/טלפון של הלקוח, דרך join ל-`bags`/`orders`/`customers` (ל-`activity_log` עצמה אין פרטי לקוח). כל שורה כוללת `id` ו-`created_at_hebrew` (תאריך עברי לפי התאריך בישראל). בהיסטוריית שקית (`bag_code`) לא מוצגות רשומות `log_entry_deleted`.
- `DELETE /api/orders/activity-log/:id` — מחיקת שורה מהיסטוריית שקית. שורה של פעולה שמשנה מצב (`picked_up`/`returned`/`customer_notified`/`customer_collected`/`manual_fix`) **מחזירה את השקית למצב שלפניה** — לפי `activity_log.prev_state` (snapshot של שדות המצב של השקית שנשמר לפני כל פעולה כזו), ולשורות ישנות בלי snapshot — לפי כלל לכל סוג פעולה (`derivePrevState`). אם אחריה יש עוד פעולות מצב על אותה שקית הן מבוטלות גם, ולכן בלי `?confirm_later=1` מוחזר 409 עם רשימתן (`needs_confirm`). לתיקון ידני ישן שאין לו מצב קודם — 409 `no_prev_state`, ו-`?log_only=1` מוחק רק את השורה. כל מחיקה נרשמת ביומן (`log_entry_deleted`).

### ספק הסת"ם (יודאיקה פלוס — "ניהול עבודה")
**מסמך חיבור נפרד לתוכנה של הספק: [`SUPPLIER_API.md`](SUPPLIER_API.md)** — מחזור החיים של שקית, כל הנתיבים עם דוגמאות, ופורמט שליחת הדוח.
- `POST /api/supplier/report` — דוח מהתוכנה של הספק על שקית, פורמט חופשי: `{bag_code, summary?, report?, mark_returned?}` או `{reports:[...]}` (עד 200). `report` = כל JSON, נשמר כמו שהוא בטבלת `bag_reports` (עמודת `json` ולא `jsonb`, כדי לשמור את סדר השדות לתצוגה). `mark_returned:true` גם מסמן הוחזרה (רק אם אצל הספק). כל דוח נרשם ביומן (`report_received`). שקית שעוד לא נאספה נדחית.
- `POST /api/supplier/deliver-direct` — `{bag_code, note?}`: שקית שאצל הספק נמסרה ללקוח בדרך אחרת ולא תחזור לחנות → סטטוס סופי `delivered_direct` (+`delivered_direct_at`, `delivered_direct_note`), יורדת מ-`with-me`, נועלת את ההזמנה, ניתנת לביטול מההיסטוריה. 409 אם השקית לא אצל הספק.
- `POST /api/supplier/note` — `{bag_code, note}`: הערה חופשית של הספק על השקית (`bags.supplier_note` + `supplier_note_at`, עד 1000 תווים; ריק = מחיקה). מוצגת בחנות ברשימה ("💬 מיכאל: …") ובמסך העריכה, ונרשמת בהיסטוריה (`supplier_note`).
- `POST /api/supplier/update` — תיקון פרטים מהספק: `{bag_code, item_type?, quantity?, item_type_note?, variant?, customer?:{first_name?,last_name?,phone?,address?}}` או `{updates:[...]}` (עד 200). רק שדות שנשלחו; `variant` מתמזג עם הקיים (null מוחק) ומנוקה לפי סוג הפריט; עוקף נעילת הזמנה; לקוח = הלקוח של ההזמנה של השקית. ביומן (`supplier_update`) נרשם רק מה שהשתנה ("כמות: מ-6 ל-7"); אין שינוי → כלום לא נרשם.
- `GET /api/supplier/report/:code` — כל הדוחות על שקית, מהחדש לישן (לאימות בצד הספק). `with-me`/`bag/:code`/`pending` מחזירים גם `report_received_at` (null = עוד לא נשלח דוח).
**ללא אימות בכוונה** (ראו יומן עדכונים) — החלטת המשתמש: מיכאל אמור להיות מחובר תמיד בלי להזין מפתח. תשתית ה-API key (`lib/apiKey.js`, `scripts/generate-api-key.js`, טבלת `api_keys`) נשארה בקוד (לא בשימוש) למקרה שירצו להחזיר הגנה בעתיד.
- `GET /api/supplier/bag/:code` — פרטי שקית לפי קוד ברקוד (הזמנה, לקוח, סוג+כמות)
- `POST /api/supplier/scan` — `{bag_code, result?}`. לסריקה בודדת (מכשיר/מצלמה) — מזהה לבד איסוף מול החזרה לפי מצב השקית הנוכחי (ראו "מודל הנתונים" למטה), כי פיזית ברור אם מדובר בביקור איסוף או ביקור החזרה. מחזיר `{action: "picked_up"|"returned"|"duplicate", bag}` או שגיאה.
- `POST /api/supplier/bulk-scan` — `{bag_codes: [...], action: "pickup"|"return"}`. חלופה לסריקה: מיכאל (או עובד החנות) יכול לעבור על רשימה (מ-`/pending` או מ-`/with-me`) ולסמן שקיות — דרך "פעולה מהירה" (קליק על שורה) או סריקה מהירה. ה-`action` כאן מפורש (לא מנוחש) כי אין "סריקה" שמזהה לבד מה המצב — זה כבר ידוע מהרשימה/הפעולה שבחרו. מחזיר `{results: [{bag_code, ok, bag} | {bag_code, ok:false, error}]}`.
- `GET /api/supplier/with-me` — כל השקיות שכרגע אצל הספק (`status=with_supplier`), **פלוס** מה שהוחזר בשעתיים האחרונות (שלב "במסירה לחנות", כדי שלא ייעלם מהרשימה מיד עם ההחזרה). כל קריאה גם מסמנת `imported_at` לכל שקית שעוד לא סומנה (הקריאה עצמה = "משיכה" לתוכנה שלו). כל שקית מחזירה `stage`: `collected` (אספתי, עוד לא נמשך) / `imported` (נכנס לתוכנה) / `returning` (במסירה לחנות) — למסך "מה אצלי", כולל מסנן לפי מצב ומספר איסוף.
- `GET /api/supplier/pending` — תצוגה מקדימה בלבד של מה שממתין לאיסוף (`status=waiting_pickup`) — **לא** השלב הראשי בזרימה (ראו הסדר הנכון ב"מודל הנתונים" למטה).
- `POST /api/supplier/customer-link` — `{phone, customer_number}`. הספק מדווח לנו איזה מספר לקוח הוא שייך לטלפון הזה אצלו (אחרי התאמה/שיוך ידני בתוכנה שלו). נשמר ב-`customers.supplier_customer_number`, ומוצע אוטומטית בפעם הבאה שאותו טלפון מוזן אצלנו ב-`/orders.html` (דרך `GET /api/orders/customer-lookup`).

### מסכי UI (סטטיים, `public/`)
- `/orders.html` — לצוות החנות, 3 טאבים:
  - "הזמנה חדשה" — טופס לקוח + שקיות מרובות, בלי מפתח API ובלי מספר הזמנה ידני (שניהם אוטומטיים). בשדה הטלפון יש הצעה אוטומטית (`blur`) אם הלקוח כבר מוכר ויש לו `supplier_customer_number` שמור.
  - "כל ההזמנות" — מיד בכניסה מוצג סיכום מהיר ("X ממתינים לאיסוף · X אצל מיכאל", מול `GET /api/orders/summary`). רשימת שקיות (לא הזמנות) עם מסננים (סוג פריט / סטטוס — כולל תתי-המצב של "חזר" / מספר איסוף) וחיפוש חופשי (שם/טלפון/מספר הזמנה), תג סטטוס לכל שקית, תאריך יצירה — עברי קודם, לועזי אחריו, והערה (אם יש) לכל שקית. כפתור **"⚡ פעולות מהירות"** פותח בחירת מטרה — **✅ לקוח עודכן** (מסמן בלי לשלוח כלום — הלקוח כבר עודכן בטלפון/בדרך אחרת), **📨 דיווח ללקוח (SMS)** (שולח הודעה אמיתית ורק בהצלחה מסמן), או **📦 מסירה ללקוח** — תמיד נשאל, לא מנוחש. שתי פעולות ה"עודכן" מקבצות לפי מספר טלפון (ראו `POST /api/orders/scan` למעלה): דיווח על שקית אחת מסמן את כל שקיות אותו טלפון שהגיעו, בלי צורך לדווח כל אחת בנפרד. במצב פעיל, **לחיצה על שורה ברשימה מבצעת את הפעולה מיד**, ולצידה כפתור "📷 סריקה מהירה" (⌨️ סורק מחובר / 📷 מצלמה) שמבצע את אותה פעולה על כל קוד שנסרק. בלי מצב פעיל, לחיצה על שורה פותחת **מסך עריכה** להזמנה שלה (פרטי לקוח + כל השקיות, הוספה/מחיקה, כפתור "🖨️ הדפס שוב" וכפתור "🕘 היסטוריה" לכל שקית — שניהם עובדים תמיד, גם על הזמנה נעולה; "היסטוריה" פותח/סוגר ברשימה את כל רשומות היומן של אותה שקית בלבד, מול `GET /api/orders/activity-log?bag_code=`) — עריכה/מחיקה זמינות רק כל עוד ההזמנה לא נעולה (ראו `locked` למעלה); אם נעולה, מוצגת הודעה והשדות הופכים לקריאה-בלבד. כפתור ↗ לדף האיסוף של מיכאל (`/supplier.html`).
  - "ניהול" — **תיקון ידני** (קוד שקית + סטטוס חדש + איפוס עדכון/איסוף, מול `PUT /api/orders/bags/:bag_code/force-status`) לתיקון טעויות בלי לעבור דרך הזרימה הרגילה ובלי קשר לנעילה; **תבנית הודעת ה-SMS** של "דיווח ללקוח" (מול `GET`/`PUT /api/orders/settings`) ניתנת לעריכה כאן בלי דיפלוי קוד; ו**יומן פעולות** (מול `GET /api/orders/activity-log`) — רשימת כל פעולה משמעותית שקרתה במערכת, מהחדשה לישנה, עם תיבת חיפוש חכם (קוד שקית / מספר הזמנה / שם / טלפון, מול `?q=`).
- `/supplier.html` — כפתור "↗ דף האיסוף" מ-`/orders.html` מוביל לכאן. 3 טאבים:
  - "סריקה" — **שני מצבים**: ⌨️ סורק מחובר (קלט מקלדת — Enter שולח) ו-📷 מצלמה (סריקה רציפה, debounce של 3 שניות לאותו קוד). שני המצבים קוראים לאותו `POST /api/supplier/scan`, שמזהה לבד איסוף/החזרה ומקבץ אוטומטית סריקות איסוף סמוכות בזמן (עד 30 דקות פער) ל"איסוף" (`collection`) אחד עם מספר רץ לצורך מעקב "ביקור #N". גם צפצוף+סיכום רץ.
  - "ממתין לאיסוף" — **מיכאל לא חייב לסרוק**: חיפוש חכם לפי שם/טלפון/כתובת, וכפתור **"⚡ איסוף מהיר"** — במצב פעיל לחיצה על שורה מסמנת אותה כנאספה מיד (ולצידו "📷 סריקה מהירה" לאותה פעולה), דרך `POST /api/supplier/bulk-scan`.
  - "מה אצלי" — אותו דפוס עם כפתור **"⚡ מסירה לחנות"**, ועוד מסנן בין שלושת תתי-המצב (`stage`): אספתי / נכנס לתוכנה / במסירה לחנות, וגם לפי מספר איסוף.
  - ללא מפתח/התחברות — משמש גם את מיכאל (או התוכנה שלו, ישירות מול ה-API) וגם את עובדי החנות כשהם סורקים בתיאום איתו.

## מודל הנתונים
`customers` (**אין מספר לקוח שלנו** — מזוהה לפי טלפון אצלנו; `supplier_customer_number` נשמר אם הספק דיווח אותו דרך `POST /api/supplier/customer-link`) → `orders` (מספר הזמנה קבוע) → `bags` (יחידת המעקב מול הספק: לכל שקית ברקוד **מספרי בלבד** — `{מספר הזמנה}{אינדקס שקית דו-ספרתי}`, למשל `123402` — בלי מפריד, כמו ברקוד חנות רגיל, ותואם למה שהמדפסת הפיזית כבר מכירה). סוגי פריט (רשימה סגורה): `tefillin_pair/head/hand, mezuzah, megillah, sefer_torah, nach, other`. `collections` — קיבוץ אוטומטי של שקיות שנסרקו באותו ביקור איסוף (חלון של 30 דקות בין סריקות), עם מספר רץ ל"ביקור #N" (ראו `getOrCreateCollection` ב-`routes/supplier.js`). `bags.imported_at` — מתי `GET /api/supplier/with-me` משך את השקית בפעם הראשונה (קובע את תת-המצב `stage` בתצוגת "מה אצלי"). `activity_log` — טבלת יומן שטוחה (לא קשורה FK לשום דבר, רק `bag_code`/`order_number` כטקסט) שכל פעולה משמעותית נכתבת אליה (ראו `lib/activityLog.js`) — למסך "ניהול". `settings` — טבלת key/value כללית (כרגע רק `sms_notify_template`), ראו `lib/settings.js`.

**הסדר הנכון מול הספק** (תוקן — ראו יומן עדכונים): **הסריקה קודמת לייבוא**, לא להפך.
1. `waiting_pickup` — ההזמנה נוצרה, ממתינה בחנות.
2. **סריקה בחנות** (`POST /api/supplier/scan`) — מיכאל **או עובד החנות בתיאום איתו** סורק כל שקית שנאספת, לפני כל ייבוא. השקית מצטרפת ל"איסוף" פתוח או פותחת חדש. → `with_supplier`.
3. רק **אחרי** הסריקה, התוכנה של מיכאל מושכת את מה שבאמת נאסף (`GET /api/supplier/with-me`) ומסדרת אצלה. מרגע זה השקית נעולה אצלנו.
4. בסיום העבודה — סריקה מהירה (או סימון ידני) של כל ההחזרות בבת אחת, עם `result` (תיקונים/הערות) לכל שקית → `returned`.
5. **בחנות**: כשהשקית חזרה, סריקה ב"סריקה ללקוח" (`/orders.html`) מסמנת `customer_notified_at` (+SMS אוטומטי) ואז בסריקה הבאה `customer_collected_at` — ה"סטטוס" (`returned`) לא משתנה, אלה שני חותמות-זמן נוספות שרק מוצגות אחרת ב-UI.

## אימות
- מיגרציה (`db/schema.sql`) רצה אוטומטית בכל עליית שרת (`server.js` מריץ `migrate()` לפני `listen`), כל עוד `DATABASE_URL` מוגדר (מוגדר ב-Railway כ-reference `${{Postgres.DATABASE_URL}}` — אף פעם לא כערך גלוי).
- מפתחות API — **לא בשימוש יותר** (ראו יומן עדכונים: גם `/api/orders/*` וגם `/api/supplier/*` ללא אימות, בהחלטת המשתמש). התשתית עצמה (טבלת `api_keys`, `lib/apiKey.js`, `scripts/generate-api-key.js`) נשארה בקוד למקרה שירצו להחזיר הגנה בעתיד — לא נמחקה.
- **הדפסה בפועל**: `lib/printQueue.js` משתמש באותו מנגנון Supabase/PostgREST שכבר עובד ב-chabad-judaica (`PRINT_URL`/`PRINT_KEY`) — צריך להגדיר אותם ידנית ב-Railway (Variables של שירות `web`) עם אותם ערכים שכבר קיימים ב-chabad-judaica, כדי שהדפסה אוטומטית ביצירת הזמנה תעבוד בפועל (בלעדיהם — מצב דמו, לא נדפס בפועל).
