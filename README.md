# judaica-stam

אתר הזמנות ייעודי לחנות יודאייקה — יצירת הזמנה, הדפסת מדבקה, ותיאום איסוף/מסירה מול ספק הסת"ם.

פרויקט נפרד מהמערכת הפנימית הגדולה של החנות (chabad-judaica). מארח על Railway (מסד נתונים + שרת + אתר), ללא Vercel.

## הרצה מקומית
```bash
npm install
npm start
```

## תשתית
- **קוד**: GitHub — `shnotik770-netizen/judaica-stam`, ענף `main` בלבד (אין branches נפרדים — כל תיקון נכנס ישירות ל-main).
- **אירוח**: Railway בלבד (ללא Vercel) — פרויקט `hazmanat-satam`.
  - שירות `web` — שרת ה-API/אתר (Node+Express). דומיין: `web-production-68f12.up.railway.app`.
  - שירות `Postgres` — מסד הנתונים המנוהל הרשמי של Railway (עם volume אוטומטי לשמירת נתונים).
- **מדפסת מדבקות**: ממשיך להשתמש בפרויקט ה-Supabase הקיים `label-printer` (לא עובר ל-Railway) — זה החיבור היחיד שנשאר מול Supabase.
- **SMS (ימות המשיח / Call2All)**: `lib/call2all.js` — עטיפה ל-API (SendSms, GetIncomingSms, GetSmsOutLog). הטוקן נקרא אך ורק מ-`process.env.CALL2ALL_TOKEN` בצד השרת, **אף פעם לא נכתב בקוד/git**. יש להגדיר אותו ידנית במשתני הסביבה של שירות `web` ב-Railway (Variables tab) — לא דרך קוד או API אוטומטי, כדי שהטוקן לא יעבור דרך שום כלי אוטומציה.

## API

### פנימי (צוות החנות)
- `POST /api/sms/send` — `{phone, message}`
- `GET /api/sms/incoming?limit=&startDate=&endDate=` — הודעות נכנסות אחרונות
- `GET /api/sms/outgoing?limit=` — יומן הודעות יוצאות
- `GET /api/sms/conversation?phone=0501234567` — כל ההתכתבות (נכנס+יוצא) מול מספר ספציפי, ממוינת לפי זמן
- `GET /api/label/:code` (`?type=qr` לברקוד QR, ברירת מחדל Code128) — מדבקת ברקוד לשקית, תמונת PNG
- `POST /api/orders` — יצירת הזמנה+שקיות: `{customer:{first_name, last_name, phone, address}, bags:[{item_type, item_type_note?, quantity}]}`. **מספר ההזמנה מונפק אוטומטית** (רץ, `order_number_seq`) — לא מתקבל מהלקוח. **אין מספר לקוח** — לקוח קיים מזוהה לפי `phone` (אם הטלפון כבר קיים, מעדכנים שם/כתובת ומשתמשים באותה רשומה; אחרת נוצר לקוח חדש). מחזיר `order_number` ו-`bag_code` לכל שקית. **מפעיל אוטומטית הדפסת מדבקה לכל שקית** (דרך `lib/printQueue.js`) — תוכן המדבקה: מספר שקית, שם, טלפון, תאריך הזמנה (עברי, ללא ניקוד, דרך `lib/hebrewDate.js`), סוג הפריט. **ללא אימות בכוונה** — החלטת החנות: לא רוצים להתעסק עם מפתחות API בצד הזה, מי שיש לו גישה לאתר יכול ליצור הזמנות.
- `GET /api/orders/customer-lookup?phone=` — אם הטלפון כבר ידוע אצלנו, מחזיר את פרטי הלקוח + `supplier_customer_number` אם כבר דווח ע"י הספק (ראו `POST /api/supplier/customer-link` למטה) — משמש להצעה אוטומטית בטופס הזמנה חדשה (ללא אימות)
- `GET /api/orders/bags?item_type=&status=&collection_number=` — רשימת שקיות עם מסננים, כולל פרטי האיסוף (`collection_number`/`collection_started_at`) אם השקית שייכת לאחד, ותאריך יצירה עברי (`created_at_hebrew`) לכל שורה — למסך "כל ההזמנות" (ללא אימות). `status` תומך גם בתתי-מצב וירטואליים של "חזר" (לא עמודה אמיתית, רק סינון): `returned_at_store` (חזר, עדיין לא עודכן ללקוח) / `notified` (עודכן, עדיין לא נאסף) / `collected` (נאסף ע"י לקוח) / `not_collected` (חזר ועדיין לא נאסף, בשימוש פנימי ע"י "סריקה ללקוח") — בנוסף לערכי הסטטוס הרגילים (`waiting_pickup`/`with_supplier`).
- `GET /api/orders` — רשימת כל ההזמנות + סיכום סטטוס שקיות לכל אחת (`bag_count`, `waiting_count`, `with_supplier_count`, `returned_count`) (ללא אימות)
- `GET /api/orders/:order_number` — צפייה בהזמנה + שקיות, כולל `locked` (true אם אחת השקיות כבר נכנסה למערכת הספק — כל סטטוס מלבד `waiting_pickup`) — משמש גם את מסך העריכה (ללא אימות)
- `PUT /api/orders/:order_number` — `{customer:{first_name,last_name,phone,address}, bags:[{bag_code,item_type,item_type_note?,quantity}]}`. עריכת פרטי לקוח ופרטי שקיות קיימות (סוג/הערה/כמות — לא מספר שקית). **רק כל עוד ההזמנה לא נעולה** (409 אם כן) — ברגע שהספק כבר קיבל שקית מההזמנה, השינוי חייב לעבור דרכו ולא דרכנו.
- `POST /api/orders/:order_number/bags` — `{item_type, item_type_note?, quantity}`. הוספת שקית חדשה להזמנה קיימת (ממשיכה את מספור השקיות, ומדפיסה לה מדבקה מיד כמו ביצירת הזמנה). רק כל עוד ההזמנה לא נעולה.
- `DELETE /api/orders/:order_number/bags/:bag_code` — מחיקת שקית בודדת מהזמנה. רק כל עוד ההזמנה לא נעולה.
- `DELETE /api/orders/:order_number` — מחיקת הזמנה+שקיותיה. רק כל עוד ההזמנה לא נעולה (ללא אימות)
- `POST /api/orders/scan` — `{bag_codes: [...], action: "notify"|"collect"}`. סריקה/סימון מהיר בחנות מול הלקוח הסופי, **רק לשקיות שכבר חזרו מהספק**. ה-`action` נבחר מראש ע"י הצוות (לא מנוחש לפי מצב השקית) — `notify` מסמן `customer_notified_at` ושולח SMS (דרך `lib/call2all.js`), `collect` מסמן `customer_collected_at` ("נאסף ע\"י לקוח"). תומך בכמה שקיות בבת אחת (מסך "סריקה ללקוח" שולח קוד אחד בכל סריקה, או כמה בבת אחת מרשימת הסימון). מחזיר `{results: [{bag_code, ok, action: "notified"|"collected"|"duplicate", order_number, customer} | {bag_code, ok:false, error}]}`. ללא אימות (כמו שאר `/api/orders`).

### ספק הסת"ם (יודאיקה פלוס — "ניהול עבודה")
מגנים ב-API key מסוג `supplier` (header `Authorization: Bearer <key>`), מונפק דרך `npm run generate-key -- "<תווית>" supplier`.
- `GET /api/supplier/bag/:code` — פרטי שקית לפי קוד ברקוד (הזמנה, לקוח, סוג+כמות)
- `POST /api/supplier/scan` — `{bag_code, result?}`. לסריקה בודדת (מכשיר/מצלמה) — מזהה לבד איסוף מול החזרה לפי מצב השקית הנוכחי (ראו "מודל הנתונים" למטה), כי פיזית ברור אם מדובר בביקור איסוף או ביקור החזרה. מחזיר `{action: "picked_up"|"returned"|"duplicate", bag}` או שגיאה.
- `POST /api/supplier/bulk-scan` — `{bag_codes: [...], action: "pickup"|"return"}`. חלופה לסריקה: מיכאל (או עובד החנות) יכול לעבור על רשימה (מ-`/pending` או מ-`/with-me`) ולסמן V על כמה שקיות בבת אחת. ה-`action` כאן כן מפורש (לא מנוחש) כי אין "סריקה" שמזהה לבד מה המצב — זה כבר ידוע מהרשימה שמסמנים ממנה. מחזיר `{results: [{bag_code, ok, bag} | {bag_code, ok:false, error}]}`.
- `GET /api/supplier/with-me` — כל השקיות שכרגע אצל הספק (`status=with_supplier`) — למסך "מה אצלי".
- `GET /api/supplier/pending` — תצוגה מקדימה בלבד של מה שממתין לאיסוף (`status=waiting_pickup`) — **לא** השלב הראשי בזרימה (ראו הסדר הנכון ב"מודל הנתונים" למטה).
- `POST /api/supplier/customer-link` — `{phone, customer_number}`. הספק מדווח לנו איזה מספר לקוח הוא שייך לטלפון הזה אצלו (אחרי התאמה/שיוך ידני בתוכנה שלו). נשמר ב-`customers.supplier_customer_number`, ומוצע אוטומטית בפעם הבאה שאותו טלפון מוזן אצלנו ב-`/orders.html` (דרך `GET /api/orders/customer-lookup`).

### מסכי UI (סטטיים, `public/`)
- `/orders.html` — לצוות החנות, 3 טאבים:
  - "הזמנה חדשה" — טופס לקוח + שקיות מרובות, בלי מפתח API ובלי מספר הזמנה ידני (שניהם אוטומטיים). בשדה הטלפון יש הצעה אוטומטית (`blur`) אם הלקוח כבר מוכר ויש לו `supplier_customer_number` שמור.
  - "כל ההזמנות" — רשימת שקיות (לא הזמנות) עם מסננים (סוג פריט / סטטוס — כולל תתי-המצב של "חזר" / מספר איסוף), תג סטטוס לכל שקית (כולל "עודכן ללקוח"/"נאסף ע\"י לקוח" כשרלוונטי), תאריך יצירה גם לועזי וגם עברי, וקישור ↗ לדף האיסוף של מיכאל (`/supplier.html`). **לחיצה על שקית פותחת מסך עריכה** להזמנה שלה (פרטי לקוח + כל השקיות, הוספה/מחיקה) — זמין רק כל עוד ההזמנה לא נעולה (ראו `locked` למעלה); אם נעולה, מוצגת הודעה והשדות הופכים לקריאה-בלבד.
  - "סריקה ללקוח" — **תמיד שואל קודם מה מטרת הסריקה** (📨 עדכון ללקוח / 📦 איסוף ע"י לקוח), לא מנחש לפי מצב השקית. אחרי הבחירה: סריקה (⌨️ סורק מחובר / 📷 מצלמה רציפה, אותו `html5-qrcode`) **או** רשימת סימון V עם חיפוש (כחלופה לסריקה) — שתיהן קוראות לאותו `POST /api/orders/scan` עם ה-action שנבחר, ותומכות בכמה שקיות בבת אחת.
- `/supplier.html` — כפתור "↗ דף האיסוף" מ-`/orders.html` מוביל לכאן. 3 טאבים:
  - "סריקה" — **שני מצבים**: ⌨️ סורק מחובר (קלט מקלדת — Enter שולח) ו-📷 מצלמה (סריקה רציפה, debounce של 3 שניות לאותו קוד). שני המצבים קוראים לאותו `POST /api/supplier/scan`, שמזהה לבד איסוף/החזרה ומקבץ אוטומטית סריקות איסוף סמוכות בזמן (עד 30 דקות פער) ל"איסוף" (`collection`) אחד עם מספר רץ לצורך מעקב "ביקור #N". גם צפצוף+סיכום רץ.
  - "ממתין לאיסוף" / "מה אצלי" — **מיכאל לא חייב לסרוק**: רשימה עם תיבות סימון (V) + חיפוש חכם לפי שם/טלפון/כתובת, ואפשרות לסמן כמה שקיות בבת אחת ("סמן שקיות שנבחרו כנאספו/כהוחזרו") דרך `POST /api/supplier/bulk-scan`.
  - דורש מפתח `supplier` (נשמר ב-localStorage) — משמש גם את מיכאל וגם את עובדי החנות כשהם סורקים בתיאום איתו.

## מודל הנתונים
`customers` (**אין מספר לקוח שלנו** — מזוהה לפי טלפון אצלנו; `supplier_customer_number` נשמר אם הספק דיווח אותו דרך `POST /api/supplier/customer-link`) → `orders` (מספר הזמנה קבוע) → `bags` (יחידת המעקב מול הספק: לכל שקית ברקוד **מספרי בלבד** — `{מספר הזמנה}{אינדקס שקית דו-ספרתי}`, למשל `123402` — בלי מפריד, כמו ברקוד חנות רגיל, ותואם למה שהמדפסת הפיזית כבר מכירה). סוגי פריט (רשימה סגורה): `tefillin_pair/head/hand, mezuzah, megillah, sefer_torah, nach, other`. `collections` — קיבוץ אוטומטי של שקיות שנסרקו באותו ביקור איסוף (חלון של 30 דקות בין סריקות), עם מספר רץ ל"ביקור #N" (ראו `getOrCreateCollection` ב-`routes/supplier.js`).

**הסדר הנכון מול הספק** (תוקן — ראו יומן עדכונים): **הסריקה קודמת לייבוא**, לא להפך.
1. `waiting_pickup` — ההזמנה נוצרה, ממתינה בחנות.
2. **סריקה בחנות** (`POST /api/supplier/scan`) — מיכאל **או עובד החנות בתיאום איתו** סורק כל שקית שנאספת, לפני כל ייבוא. השקית מצטרפת ל"איסוף" פתוח או פותחת חדש. → `with_supplier`.
3. רק **אחרי** הסריקה, התוכנה של מיכאל מושכת את מה שבאמת נאסף (`GET /api/supplier/with-me`) ומסדרת אצלה. מרגע זה השקית נעולה אצלנו.
4. בסיום העבודה — סריקה מהירה (או סימון ידני) של כל ההחזרות בבת אחת, עם `result` (תיקונים/הערות) לכל שקית → `returned`.
5. **בחנות**: כשהשקית חזרה, סריקה ב"סריקה ללקוח" (`/orders.html`) מסמנת `customer_notified_at` (+SMS אוטומטי) ואז בסריקה הבאה `customer_collected_at` — ה"סטטוס" (`returned`) לא משתנה, אלה שני חותמות-זמן נוספות שרק מוצגות אחרת ב-UI.

## אימות
- מיגרציה (`db/schema.sql`) רצה אוטומטית בכל עליית שרת (`server.js` מריץ `migrate()` לפני `listen`), כל עוד `DATABASE_URL` מוגדר (מוגדר ב-Railway כ-reference `${{Postgres.DATABASE_URL}}` — אף פעם לא כערך גלוי).
- מפתחות API — טבלת `api_keys`, נשמר רק hash, עם `scope` (`internal`/`supplier`) שקובע לאיזה נתיבים מפתח מסוים מורשה (403 אם לא תואם — כדי שמפתח הספק לא יוכל ליצור הזמנות, ולהפך). `scripts/generate-api-key.js` קיים לשימוש מקומי (`npm run generate-key -- "תווית" internal|supplier`) אם יש `DATABASE_URL` זמין; בפועל (כשאין גישה למחשב עם חיבור ל-DB) נוצר מפתח חדש דרך Railway Function זמני שמריץ את אותה לוגיקה בתוך הסביבה של Railway (יש לו גישה אוטומטית ל-`DATABASE_URL` בלי שאף אחד צריך לראות את הסיסמה), ונמחק מיד אחרי.
- מפתח "יודאיקה פלוס" (`scope=supplier`) הופק ונבדק מקצה לקצה (יצירת הזמנה → `bag/:code` → `scan` איסוף → `scan` החזרה עם תוצאה → מצב סופי) מול הסביבה החיה.
- **הדפסה בפועל**: `lib/printQueue.js` משתמש באותו מנגנון Supabase/PostgREST שכבר עובד ב-chabad-judaica (`PRINT_URL`/`PRINT_KEY`) — צריך להגדיר אותם ידנית ב-Railway (Variables של שירות `web`) עם אותם ערכים שכבר קיימים ב-chabad-judaica, כדי שהדפסה אוטומטית ביצירת הזמנה תעבוד בפועל (בלעדיהם — מצב דמו, לא נדפס בפועל).
